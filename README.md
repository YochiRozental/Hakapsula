# מערכת ניהול קליניקות — קביעת תורים

מערכת לניהול תורים לחדרי קליניקה: חדר 1, חדר 2, חדר סדנאות, וחדר 1+2 (משולב).
הזמנת חדר 1+2 חוסמת אוטומטית גם את חדר 1 וגם את חדר 2 באותו טווח זמן, ולהפך — כדי למנוע התנגשות פיזית. חדר הסדנאות עצמאי לחלוטין.

## סטאק טכנולוגי

- **Next.js 16** (App Router) + TypeScript + Tailwind CSS
- **PostgreSQL** + **Prisma ORM**
- **Auth.js (NextAuth v5)** — התחברות/הרשמה עם אימייל וסיסמה
- **Express + yemot-router2** — שרת IVR נפרד לקביעת תורים בטלפון דרך ימות המשיח (`src/ivr/`)

## הערות סביבה

- ה-Postgres בקונטיינר מפורסם על פורט **5433** (לא 5432), כדי לא להתנגש עם התקנת Postgres מקומית שכבר קיימת על המחשב. אם תרצו לשנות זאת, עדכנו גם את `docker-compose.yml` וגם את `DATABASE_URL` ב-`.env`.
- `npm run dev` מריץ את השרת עם `--webpack` (ולא עם Turbopack, שהוא ברירת המחדל של Next 16) כדי לעקוף בעיית טעינת גופנים מ-Google Fonts בסביבת הפיתוח הנוכחית.

## הרצה מקומית

1. הפעילו את בסיס הנתונים (Postgres) עם Docker:

   ```bash
   docker compose up -d
   ```

2. התקינו תלויות (אם עדיין לא הותקנו):

   ```bash
   npm install
   ```

3. הריצו מיגרציה ליצירת הטבלאות + הזרעת נתונים ראשוניים (חדרים + משתמש מנהל):

   ```bash
   npm run db:migrate
   npm run db:seed
   ```

   פרטי התחברות ברירת מחדל למנהל: `admin@clinics.local` / `Admin12345!`
   **חשוב להחליף סיסמה זו בסביבת ייצור.**

4. הריצו את השרת:

   ```bash
   npm run dev
   ```

   האתר יהיה זמין בכתובת http://localhost:3000

## מבנה המערכת

- `/` — עמוד הבית
- `/register`, `/login` — הרשמה/התחברות (חובה כדי לקבוע תור)
- `/booking` — קביעת תור: בחירת חדר בלחיצה, בחירת תאריך בלוח שנה חודשי, ובחירת שעה מרשת שעות שמציגה ויזואלית אילו שעות תפוסות/פנויות/עברו
- `/booking/my` — התורים שלי (כולל ביטול)
- `/admin` — לוח בקרה למנהל (רק למשתמשי ADMIN)
- `/admin/calendar` — לוח שנה למנהל: לוח חודשי לבחירת יום (עם נקודה לימים שיש בהם תורים) + תצוגת יום עם עמודה לכל חדר וכל התורים ממוקמים לפי שעה, כולל ביטול בלחיצה
- `/admin/appointments` — טבלת כל התורים עם סינון + קביעת תור ידנית עבור לקוח קיים
- `/admin/rooms` — הפעלה/השבתה של חדרים
- `/admin/users` — ניהול משתמשים והרשאות

מניעת ההתנגשויות מתבצעת בשכבת השרת בתוך טרנזקציה (`src/lib/booking.ts`), כך שגם בקשות מקבילות לא יכולות ליצור התנגשות בין תורים.

## אינטגרציה עם ימות המשיח (IVR טלפוני)

יש שרת נפרד וקטן (`src/ivr/server.ts`) שמאפשר קביעת תור דרך שיחת טלפון, באמצעות מודול ה-API של ימות המשיח וספריית [yemot-router2](https://github.com/ShlomoCode/yemot-router2). הוא משתמש באותה פונקציית ליבה בדיוק כמו האתר (`createAppointment` ב-`src/lib/booking.ts`), כך שכל כללי מניעת ההתנגשויות, שעות הפעילות ומשכי התור זהים לחלוטין בין האתר לטלפון.

**חשוב:** בניגוד לאתר עצמו, שרת ה-IVR **חייב לרוץ כתהליך Node קבוע** (VPS/שרת עם Docker וכדומה) ולא כפונקציות serverless — כי הספרייה שומרת את מצב השיחה (איפה המתקשר נמצא בתהליך) בזיכרון השרת בין בקשה לבקשה, עד לתשובה הבאה מהמתקשר.

### איך זה עובד

הזרימה בנויה כמה **שלוחות נפרדות** בפאנל ימות המשיח, שמנווטות ביניהן עם `go_to_folder` — כל שלוחה אחראית על פעולה אחת בלבד:

1. **שלוחת הבדיקה** (נקודת הכניסה לשיחה) — בודקת את מספר הטלפון של המתקשר (Caller ID) מול שדה `phone` של המשתמשים במערכת. זו ה"התחברות" — אין קוד סודי בשלב הזה, הזיהוי הוא לפי Caller ID בלבד. בהתאם לתוצאה, מנתבת מיד את השיחה:
   - מספר רשום → **שלוחה 1** ("מחוברים").
   - מספר לא רשום → **שלוחה 2** ("לא רשום").
2. **שלוחה 1 — מחוברים**: מתנהלת שיחת קביעת תור קצרה עם הקשות (לא צריך להקליד כלום, רק להקיש מספרים): בחירת חדר → תאריך → שעה → משך → אישור. בסיום נקרא `createAppointment(..., source: "IVR")` — בדיוק כמו קביעת תור מהאתר, כולל בדיקת התנגשויות. בטבלת `Appointment` השדה `source` (`WEB`/`IVR`/`ADMIN`) מציין תמיד מאיפה הגיע כל תור.
3. **שלוחה 2 — לא רשום**: מציגה למתקשר תפריט קצר —
   - **1 = הרשמה**: אומר את שמו המלא (זיהוי דיבור), בוחר קוד סודי אישי בן 4 ספרות ומקיש אותו פעמיים לאישור. נוצר משתמש חדש (`role: CLIENT`) עם השם, מספר הטלפון והקוד הסודי (מוצפן באותה שיטה כמו סיסמאות אתר — `bcrypt`). לחשבון שנוצר כך **אין כתובת אימייל** (השדה `email` הפך לאופציונלי בסכמה), ולכן לא ניתן להתחבר איתו לאתר — הוא משמש רק לזיהוי טלפוני לפי Caller ID, בדיוק כמו משתמש שנרשם באתר ועדכן מספר טלפון. מיד לאחר ההרשמה, השיחה מנותבת לשלוחה 1 (מחוברים) לקביעת התור.
   - **2 = שמיעת הסבר על המערכת**: מנתב לשלוחה 3.
   - **3 (או כל הקשה אחרת/ללא מענה) = ניתוק**.
4. **שלוחה 3 — הסבר על המערכת**: שלוחה קיימת בפאנל שלכם (הקלטה/תפריט), לא חלק מהקוד שלנו.

שדה `phone` ייחודי (`@unique`) במסד הנתונים, כדי שלא ייווצרו שני משתמשים לאותו מספר טלפון בין רישום באתר לרישום בטלפון.

מיפוי השלוחות (1/2/3) קבוע בקוד ב-`MEMBERS_EXTENSION`/`NOT_REGISTERED_EXTENSION`/`EXPLANATION_EXTENSION` בתחילת `src/ivr/booking-flow.ts` — אם מספרי השלוחות אצלכם בפאנל שונים, יש לעדכן שם.

### הרצת שרת ה-IVR

```bash
npm run ivr        # הרצה רגילה
npm run ivr:dev     # הרצה עם ריסטארט אוטומטי בשינויי קוד, לפיתוח
```

השרת מאזין כברירת מחדל על פורט 3001 (`IVR_PORT` ב-`.env`). בעליה הוא מדפיס ללוג את תבנית שלוש כתובות ה-API שצריך להזין בפאנל של ימות המשיח. הסוד עצמו (`IVR_SHARED_SECRET`) לא מודפס ללוג, ויש להחליף את `<IVR_SHARED_SECRET>` בערך שב-`.env`:

```
[ivr] שלוחת הבדיקה (הכניסה לשיחה) -> http://<your-domain>:3001/check-<IVR_SHARED_SECRET>
[ivr] שלוחה 1, "מחוברים" -> http://<your-domain>:3001/booking-<IVR_SHARED_SECRET>
[ivr] שלוחה 2, "לא רשום" -> http://<your-domain>:3001/not-registered-<IVR_SHARED_SECRET>
```

הסיומת האקראית (`IVR_SHARED_SECRET` ב-`.env`, זהה לשלושת הנתיבים) היא אמצעי אבטחה — כדי שרק מי שמכיר את הכתובת המלאה (כלומר, ימות המשיח שהוגדר עם ה-URL הזה) יוכל לגשת לנתיב. **אל תשתפו את הכתובות האלה בשום מקום ציבורי, ואם דלפו — שנו את `IVR_SHARED_SECRET` והפעילו מחדש (זה משנה את כל שלוש הכתובות יחד).**

בייצור צריך שהכתובות יהיו נגישות מהאינטרנט (ימות המשיח קורא להן מהשרתים שלהם), כלומר יידרש דומיין/פורט פתוח, ומומלץ מאוד HTTPS מול שרת proxy (nginx/caddy) מול פורט 3001 במקום לחשוף אותו ישירות.

### אילו שלוחות להגדיר בפאנל הניהול של ימות המשיח

נדרשות **ארבע שלוחות**: שלוש שמפנות לשרת שלנו (בדיקה, מחוברים, לא-רשום), ואחת רגילה (הסבר על המערכת) שכבר קיימת אצלכם ולא קשורה לקוד:

1. **שלוחת הכניסה לשיחה** (יכולה להיות השלוחה הראשית של הקו) — סוג `type=api`, ושדה `api_link` = כתובת "שלוחת הבדיקה" מהלוג.
2. **שלוחה 1** — סוג `type=api`, ושדה `api_link` = כתובת "שלוחה 1, מחוברים" מהלוג.
3. **שלוחה 2** — סוג `type=api`, ושדה `api_link` = כתובת "שלוחה 2, לא רשום" מהלוג.
4. **שלוחה 3** — השלוחה הקיימת אצלכם עם ההסבר/ההקלטה על המערכת, ללא שינוי.

בכל שלוש שלוחות ה-API השאירו את שיטת השליחה כברירת המחדל (GET) — אין צורך ב-`api_url_post=yes`.

**חשוב:** מספרי השלוחות "1", "2", "3" חייבים להתאים למה שמוגדר בקבוע `MEMBERS_EXTENSION`/`NOT_REGISTERED_EXTENSION`/`EXPLANATION_EXTENSION` בתחילת `src/ivr/booking-flow.ts` (שם הם `/1`, `/2`, `/3` — נתיבים מוחלטים משלוחת השורש). אם בפאנל שלכם המספור שונה, עדכנו את הקבועים האלה בקוד בהתאם.

### בדיקה לפני חיבור לקו אמיתי

אפשר לדמות שיחה נכנסת מימות המשיח עם `curl`, בלי לחכות לקו טלפון אמיתי. כל בקשה חייבת לכלול `ApiPhone`, `ApiDID`, `ApiExtension` ו-`ApiCallId` זהה לאורך כל השיחה המדומה. לדוגמה, בדיקת שלוחת הבדיקה:

```bash
curl -G "http://localhost:3001/check-<הסיומת-הסודית>" \
```

התשובה תהיה `go_to_folder=/1` או `go_to_folder=/2` בהתאם לכך שהמספר רשום או לא. לבדיקת שלוחה 1 או 2 עצמן (שממשיכות בשאלות `read`, למשל `http://localhost:3001/booking-<הסיומת-הסודית>` או `.../not-registered-<הסיומת-הסודית>`), התשובה הראשונה תהיה שורת טקסט כמו `read=t-...=val_1,...` — זו השאלה הבאה שהמערכת "משמיעה". כדי "להקיש" תשובה, שולחים בקשה נוספת עם אותם פרמטרים + `val_1=<הבחירה>`, וכך הלאה עם `val_2`, `val_3` וכו', בהתאם למספר השאלות שכבר נענו.
